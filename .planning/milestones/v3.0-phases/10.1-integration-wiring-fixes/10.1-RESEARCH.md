# Phase 10.1: Integration Wiring Fixes - Research

**Researched:** 2026-02-28
**Domain:** Python numeric conventions, dataclass wiring, frozenset filtering, module re-exports
**Confidence:** HIGH

## Summary

Phase 10.1 is a pure surgical-fix phase targeting four cross-phase integration gaps (INT-01 through INT-04) discovered during the v3.0 milestone audit. All four gaps are in already-implemented files — no new modules are required, only targeted edits. The scope is tight: one function body change, two aggregation replacements, one dataclass field addition + one function call change, one frozenset extension, and one import re-export.

The highest-complexity gap is INT-01 (`mc_dist` wiring through the sweep grid). It requires adding `mc_dists: list[AllocationDistribution] | None` to `SweepConfig`, adding `mc_dist` to `SweepCell`, extending `_enumerate_cells()` to include it in the cartesian product, and passing it in `_run_cell()`. The TOML loader must also handle the optional `mc_dists` axis. The remaining three gaps (INT-02, INT-03, INT-04) are one-to-three-line edits.

**Primary recommendation:** Implement all four gaps in a single focused plan — each is independent, no gap blocks another, and the combined test surface is small enough to cover in one wave.

### Pattern 1: NaN-for-degenerate-inputs Convention

**What:** Functions that compute metrics over weight arrays return `float(np.nan)` when the input is degenerate (zero-weight, zero-sum). This is the established project convention from Phase 8 (`_gini`, `_enp`).

**When to use:** Any metric helper that could receive zero-weight arrays.

**Current non-conforming code in `metrics.py` line 59-60:**
```python
def _nakamoto(weights: np.ndarray) -> int:
    """Minimum number of voters controlling > 50% of total weight."""
    if len(weights) == 0 or weights.sum() == 0:
        return 0  # BUG: should be float(np.nan)
```

**Corrected pattern:**
```python
def _nakamoto(weights: np.ndarray) -> int | float:
    """Minimum number of voters controlling > 50% of total weight.

    Returns np.nan for zero-weight arrays (NaN-for-degenerate-inputs convention).
    """
    if len(weights) == 0 or weights.sum() == 0:
        return float(np.nan)  # FIXED
    sorted_w = np.sort(weights)[::-1]
    cumsum = np.cumsum(sorted_w)
    threshold = 0.5 * sorted_w.sum()
    idx = np.searchsorted(cumsum, threshold, side='left')
    return int(idx + 1)
```

**Note:** The return type annotation must change from `int` to `int | float` (or `float`) to accommodate `np.nan`. The `NakamotoResult` dataclass currently types `.legacy` and `.signals` as `dict[str, int]` — these should become `dict[str, int | float]` or `dict[str, float]` after the fix.

### Pattern 2: np.nanmean for metric aggregation

**What:** When aggregating per-proposal metric values that may contain `np.nan` (degenerate proposals), use `np.nanmean` so NaN values are silently excluded rather than poisoning the aggregate.

**Current bug in `sweep.py` lines 359-360:**
```python

'nakamoto_signals_mean': float(np.mean(list(nakamoto.signals.values()))) if nakamoto.signals else float('nan'),
```

**Corrected pattern (matching the ENP lines above it, lines 357-358):**
```python
'nakamoto_legacy_mean': float(np.nanmean(list(nakamoto.legacy.values()))) if nakamoto.legacy else float('nan'),
'nakamoto_signals_mean': float(np.nanmean(list(nakamoto.signals.values()))) if nakamoto.signals else float('nan'),
```

### Anti-Patterns to Avoid

- **Returning `int(0)` for degenerate Nakamoto:** The old behavior returns `0`, which is outside the valid Nakamoto range `[1, n_voters]`, and propagates silently through `np.mean` as a valid value rather than being excluded. Use `float(np.nan)` and `np.nanmean`.
- **Using `np.mean` with potentially NaN-containing arrays:** When per-proposal values may contain `NaN` (from degenerate proposals), `np.mean` propagates the NaN to the aggregate. Use `np.nanmean` to skip degenerate cells silently.
- **Modifying `_make_failed_row` schema:** The `_make_failed_row()` helper returns NaN for all metric columns; if `mc_dist` is added as a grid column, `_make_failed_row` must also emit it. However, `mc_dist` is an object — the summary_df stores the grid params as scalars. The `mc_dist` object itself should not be stored in the DataFrame. Use a string representation or index if needed, or simply add `mc_dist_label` as an optional string column.
- **Deeply nested TOML for AllocationDistribution:** TOML cannot directly serialize Python objects. Do not attempt to load `AllocationDistribution` instances from TOML in this phase — keep TOML mc_dists as `None` / out of scope unless explicitly required.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| NaN-safe aggregation | Custom filter-then-mean | `np.nanmean` | stdlib numpy, tested, handles edge cases |
| Cartesian product | Manual nested loops | `itertools.product` | Already in use, already correct |
| Module re-exports | Complex import shims | Direct `from X import Y` in `__init__.py` | Standard Python pattern |

**Key insight:** All four fixes use only existing stdlib/numpy patterns already present in the codebase. No custom infrastructure needed.

## Common Pitfalls

### Pitfall 1: NakamotoResult type annotation mismatch

**What goes wrong:** After changing `_nakamoto()` to return `float(np.nan)`, the `NakamotoResult` dataclass has `dict[str, int]` annotations. If tests assert `isinstance(coeff, int)`, they will fail on NaN cells.

**Why it happens:** The return type of `_nakamoto()` changes from `int` to `int | float`. The result dataclass and any tests that assert `isinstance(coeff, int)` need updating.

**How to avoid:** Update the `NakamotoResult` dataclass annotations from `dict[str, int]` to `dict[str, int | float]`. Update test assertions from `isinstance(coeff, int)` to `isinstance(coeff, (int, float))`. The existing test in `test_metrics.py::test_nakamoto_coefficient` currently asserts `coeff >= 1` — this will correctly fail for degenerate proposals that return `np.nan`, so the test fixture must not contain all-zero-weight proposals (it likely doesn't).

**Warning signs:** `TypeError` or `AssertionError` in `test_nakamoto_coefficient` after the fix.

### Pitfall 2: `_make_failed_row` column schema mismatch when mc_dist is added

**What goes wrong:** After adding `mc_dist` to `SweepCell`, `_run_cell()` may emit a row with `mc_dist_label` column, but `_make_failed_row()` does not, causing DataFrame column misalignment.

**Why it happens:** Both success and failure paths must produce rows with identical column sets for `pd.DataFrame(rows)` to produce a clean DataFrame.

**How to avoid:** Add a `mc_dist_label` (or equivalent string representation) column to both `_run_cell()` return dict and `_make_failed_row()` dict simultaneously, if tracking mc_dist identity in the DataFrame is desired. If `mc_dist` objects are not tracked in the summary_df (just passed to generate_scenario), this pitfall is avoided entirely.

**Recommendation:** Do not store `mc_dist` objects in summary_df. Use `mc_dist_label: str | None = None` in the row dicts if tracking is needed.

### Pitfall 3: TOML `mc_dists` axis serialization in `config.json` export

**What goes wrong:** `run_sweep()` auto-exports `config.json` using `json.dump(config_dict, ...)`. If `mc_dists` is a list of `AllocationDistribution` objects, `json.dump` will fail (objects are not JSON-serializable).

**Why it happens:** `AllocationDistribution` is a Python dataclass, not JSON-primitive.

**How to avoid:** When exporting `config.json`, serialize `mc_dists` as a list of `repr()` strings or `dataclasses.asdict()` output, or simply omit the `mc_dists` field from the JSON export. The audit's INT-01 success criterion only requires the axis exist and be passed through — not that it round-trip through JSON.

### Pitfall 4: `pipeline.py` `data_cfg` filter strips object parameters

**What goes wrong:** Even after adding `'mc_dist'` and `'vote_timing'` to `_GENERATE_SCENARIO_KEYS`, the dict filter `{k: v for k, v in cfg.get('data', {}).items() if k in _GENERATE_SCENARIO_KEYS}` only picks them up if they are **in the config dict**. They typically come as explicit function parameters, not via the TOML config dict.

**Why it happens:** The pipeline's config loading (TOML/dict path) doesn't know about object-typed parameters like `AllocationDistribution`. These must be injected via `run_pipeline()` function parameters, not via config dict.

**How to avoid:** Add explicit `mc_dist` and `vote_timing` keyword arguments to `run_pipeline()` and inject them into `data_cfg` after the dict filter (as shown in Pattern 4 above). This is the correct design: TOML controls scalar params, code controls object params.

### Pitfall 5: Test regression on `_nakamoto()` for valid cases

**What goes wrong:** After changing `_nakamoto()` to return `float(np.nan)` for empty/zero-weight arrays, the function still returns `int` for valid arrays. But `NakamotoResult.legacy: dict[str, int]` annotation is now stale.

**Why it happens:** Python doesn't enforce type annotations at runtime, but mypy/pyright will flag the mismatch.

**How to avoid:** Change annotation to `dict[str, int | float]`. Since `np.nan` is a float, the return value of `_nakamoto()` for degenerate inputs is `float`, for normal inputs is `int`. Keep `int` for the non-degenerate path (no regression on normal tests).

## Open Questions

1. **Should `mc_dist_label` be stored in summary_df?**
   - What we know: `SweepCell.mc_dist` is an `AllocationDistribution` object. The summary_df needs to identify which mc_dist was used for each row.
   - What's unclear: Whether a string repr (e.g., `"BetaDistribution(a=2.0, b=5.0)"`) is sufficient, or whether a dict serialization is needed for downstream analysis.
   - Recommendation: Use `repr(cell.mc_dist)` as a string label column `mc_dist_label` in the row dict. Store `None` when `mc_dist=None`. This is JSON-safe, human-readable, and reversible for analysis.

2. **Should `_make_failed_row` include `mc_dist_label`?**
   - What we know: All rows in the summary_df must have identical schema.
   - What's unclear: Whether to add it unconditionally.
   - Recommendation: Yes — add `mc_dist_label: str | None` to both `_run_cell()` return dict and `_make_failed_row()`.

3. **TOML support for mc_dists axis**
   - What we know: The success criterion says "SweepConfig accepts mc_dists axis" but does not mention TOML support.
   - What's unclear: Whether the TOML loader should support `mc_dists` via string type names + params.
   - Recommendation: Out of scope for Phase 10.1. Keep `load_sweep_config()` setting `mc_dists=None`. TOML support is a v3.1 enhancement.
