# Eligibility Requirements

Signals uses the same `ParticipantRequirements` structure for both proposers and supporters:

```solidity
struct ParticipantRequirements {
    address token;              // Token used for eligibility checks
    uint256 minBalance;         // Minimum current balance required (in wei)
    uint256 minHoldingDuration; // Minimum blocks tokens must be held (requires IVotes)
    uint256 minLockAmount;      // Minimum tokens that must be locked
}
```

Eligibility mode is inferred from field values — there is no explicit enum:

| Mode | `minBalance` | `minHoldingDuration` | Notes |
|---|---|---|---|
| **Open** — no requirement | `0` | `0` | Anyone can participate |
| **Min Balance** | `> 0` | `0` | Current ERC20 balance check |
| **Has Held Tokens** | `> 0` | `> 0` | Historical snapshot check; requires `IVotes` on `token` |

**`minLockAmount`** can be combined with any mode to require a minimum lock per action.

For a full explanation of each mode, constraints, and worked examples, see
[Eligibility Parameters](/reference/board-configuration/eligibility-parameters).

---

## Key Constraints

- `token` cannot be `address(0)`.
- `minHoldingDuration > 0` requires `minBalance > 0` **and** an `IVotes`-compatible token (e.g. `ERC20Votes`). Plain ERC20s are not supported for duration checks.
- `minLockAmount` must be ≤ `minBalance`.

Both `proposerRequirements` and `supporterRequirements` are **immutable after deployment**.
